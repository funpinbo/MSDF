# 내부 동작

> **현재 상태: 구현 전.** 이 문서는 구현할 구조를 설명합니다. 쓰는 데 필요한 내용은 아니지만,
> 성능이나 실패 상황을 이해하고 싶을 때 도움이 됩니다.

## 프로세스 구조

MSDF는 별도 서버에 코드를 올리는 방식이 아니라 **라이브러리**입니다. 프로세스는 두 종류입니다.

```text
          msdf up (엔진 프로세스)
   ┌──────────────────────────────┐
   │  Scheduler + Planner + IAM   │
   │  SQLite (메타데이터)         │
   │  로컬 웹 UI                  │
   └──┬────────────┬──────────┬───┘
      │            │          │        HTTP 양방향
  ┌───┴────┐  ┌────┴───┐  ┌───┴─────┐
  │chatbot │  │ search │  │embedding│   사용자가 평소대로 실행하는 서비스
  │+start()│  │+start()│  │+start() │   = 그 서비스의 Worker
  └────────┘  └────────┘  └─────────┘
```

- **엔진** (`msdf up`): 설정 파일을 들고, 요청을 받아 계획을 세우고, 단계를 서비스에 나눠 줍니다. 서비스를 띄우거나 사용자 코드를 import하지 않습니다.
- **서비스 프로세스**: 사용자가 실행합니다. `start()`가 작은 수신 서버를 띄워, 엔진이 보낸 단계를 실행합니다.
- **데이터는 엔진을 거치지 않습니다.** 서비스 프로세스가 저장소에서 직접 읽고 씁니다. 엔진은 "어디에 넣을지"와 ID 같은 메타데이터만 다룹니다. 큰 데이터가 중앙을 지나가지 않습니다.

## 엔진 구성 요소

| 구성 요소 | 책임 |
| --- | --- |
| IAM | 요청과 DAG의 흐름이 규칙에 맞는지 판정 |
| Planner | DAG의 결과에서 거꾸로 올라가며 실행할 단계 목록(Recipe)을 만듦. 캐시된 단계는 제외 |
| Artifact 테이블 | 데이터마다 출처, 생성 시각, 체크섬 같은 메타데이터를 보관. 실제 데이터는 갖지 않음 |
| Scheduler | 단계를 큐에 넣고 쉬는 서비스 인스턴스에 보냄. 시간 초과·중복 실행 관리 |
| Resolver | 설정에 따라 데이터를 저장·읽기·삭제. 서비스 프로세스 안에서 돌며 DB 종류를 아는 유일한 부분 |

## ID 두 개

| | 요청의 정체 (`lineage_key`) | 데이터의 정체 (`artifact_id`) |
| --- | --- | --- |
| 만드는 시점 | 계산 **전** | 저장 **직후** |
| 재료 | 서비스, Action, 버전, 출력 슬롯, 입력 슬롯별 데이터 ID, (첫 단계라면) params | 부모 데이터 ID들, 요청의 정체, 세대(generation) |
| 쓰임 | 캐시 확인, 중복 실행 방지 | 데이터 위치 찾기, 출처 추적 |

요청의 정체를 계산 전에 정할 수 있으므로 "이미 만든 적이 있는가"를 실행하지 않고 판단합니다.
데이터 ID에는 부모 ID가 들어가므로 단계를 거칠수록 출처가 쌓입니다. 사용자 코드에는 둘 다 나오지 않습니다.

## 한 단계가 실행되는 과정

```text
Scheduler ── 단계 실행 요청 ──▶ 서비스 프로세스
  1. 입력 데이터를 저장소에서 읽어 Action 인자로 넣는다
  2. Action을 실행한다. 실행 중에는 주기적으로 "살아 있다"고 알린다
  3. 반환값을 출력 슬롯별로 저장하고 데이터 ID를 받는다
  4. 메타데이터를 Artifact 테이블에 등록한다
  5. 완료를 보고한다 → Scheduler가 다음 단계를 보낸다
```

- 한 서비스 프로세스는 **한 번에 한 단계만** 실행합니다. 처리량을 늘리려면 같은 서비스를 여러 개 띄웁니다.
- 동기 함수는 스레드 풀에서, `async` 함수는 그대로 실행합니다. 사용자 서비스 코드가 같은 프로세스에서 돌고 있어도 막지 않습니다.

### 단계 상태

```text
queued → leased → running → saved → done
                     │
                     └──▶ failed ──▶ (의존하던 단계) cancelled
```

`saved`는 "저장은 끝났지만 아직 등록 전"입니다. 이 사이에 죽어도 다시 시도하면 저장소가 같은 데이터 ID를 돌려주므로, 데이터를 두 번 쓰지 않고 등록만 다시 합니다.

## 실패 처리

| 상황 | 동작 |
| --- | --- |
| Action이 예외를 냄 | `retries`만큼 재시도. 간격은 `retry_delay * 2**attempt` |
| 서비스 프로세스가 죽음 | "살아 있다" 신호가 끊겨 임대(lease)가 만료되면 단계를 큐로 되돌려 다른 인스턴스에서 다시 실행 |
| 저장은 됐는데 등록 실패 | `saved` 상태에서 등록만 재시도 |
| 재시도 소진 | 단계 `failed`, 의존 단계 `cancelled`, 요청한 모든 서비스의 `on_fail` 호출 |
| 여러 서비스가 같은 결과를 동시에 요청 | 계산은 한 번만, 배달은 요청 수만큼 |
| 엔진이 재시작됨 | 단계 상태가 DB에 있으므로 이어서 진행 |

기본 시간 값은 임대 60초, "살아 있다" 신호 20초 주기이며 모두 설정으로 바꿀 수 있습니다. 10분 걸리는 Action도 신호를 계속 보내므로 임대를 길게 잡을 필요가 없습니다.

## 데이터 보관

- 같은 요청의 최근 N세대, 같은 자리에서 버전만 바뀐 복제본의 최근 M개를 **hot** 영역에 두고 캐시로 씁니다. N과 M은 사용자가 정합니다.
- 그보다 오래된 메타데이터는 **cold** 영역으로 옮겨 추적용으로만 남깁니다. 캐시 확인은 hot만 봅니다.
- 데이터 본체는 옮기거나 지우지 않습니다. 보관 기간은 사용자 DB의 정책입니다.
- 저장소에서 본체가 사라졌으면(`load` 실패) 캐시가 없는 것으로 보고 새로 만듭니다.

## 삭제

데이터는 바뀌지 않으므로 없애는 길은 삭제 요청뿐입니다.

1. 서비스가 삭제를 요청합니다.
2. IAM `delete` 규칙을 검사합니다.
3. 엔진이 **삭제 표시를 먼저** 남깁니다. 이 순간부터 캐시로 쓰이지 않습니다.
4. 저장소가 본체를 지웁니다. 실패하면 표시를 둔 채 다시 시도합니다.

표시를 먼저 하므로 본체 삭제가 실패해도 지운 데이터가 서빙되지 않습니다.
기본으로 하위 데이터는 남겨 두고 "부모 삭제됨"으로 표시만 하며, `cascade`를 주면 하위까지 지웁니다.

## 엔진의 저장소

엔진은 메타데이터를 로컬 SQLite 파일(`.msdf/msdf.db`) 하나에 둡니다.

- **DB에 쓰는 프로세스는 엔진 하나뿐**입니다. 서비스들이 큐를 직접 읽어 가지 않고 엔진이 밀어 주는 구조라 SQLite의 동시 쓰기 문제를 피합니다.
- WAL 모드를 써서 엔진이 쓰는 동안 UI가 상태를 읽을 수 있습니다.
- 0.x 동안은 버전이 바뀌어 DB 구조가 달라지면 자동 변환하지 않고 `.msdf/msdf.db`를 지우라고 안내합니다. 이 파일에는 캐시와 실행 기록만 있으므로, 지워도 저장소에 있는 실제 데이터는 그대로입니다.
- 단계가 아주 많아 SQLite가 병목이 되면 PostgreSQL로 바꿀 수 있도록 저장 계층을 분리해 둡니다.

## 성능

한 단계의 비용은 대부분 **데이터를 읽고 쓰는 시간**과 Action 자체의 계산입니다. 엔진의 계획·큐 처리는 그에 비해 작습니다. 그래서 다음을 우선합니다.

- 데이터가 엔진을 거치지 않게 한다.
- 열 지향 포맷(Parquet)처럼 작고 빠른 기본 포맷을 쓴다.
- 캐시로 계산 자체를 건너뛴다.
- 단계마다 대기·실행·저장 시각을 기록해, 어디가 느린지 UI에서 볼 수 있게 한다.

## 웹 UI

`msdf up`과 함께 로컬 웹 UI가 뜹니다(Vue 3 기반 예정).

- DAG를 그래프로 보고, 이후에는 편집까지 할 수 있게 합니다. 편집 결과는 DAG 파일로 저장됩니다.
- 각 단계의 상태와 실패한 위치, 실패 원인을 보여 줍니다.
- 서비스 코드에서 찾은 `order()` 호출을 보여 줘, 어느 서비스가 어떤 결과물을 요청하는지 한눈에 볼 수 있습니다.
