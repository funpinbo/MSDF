# 내부 동작

쓰는 데 꼭 필요한 내용은 아니지만, 성능이나 실패 상황을 이해하고 싶을 때 도움이 됩니다.

## 프로세스 구조

MSDF는 별도 서버에 코드를 올리는 방식이 아니라 **라이브러리**입니다. 프로세스는 두 종류입니다.

```text
          msdf up (엔진 프로세스)
   ┌──────────────────────────────┐
   │  Scheduler + Planner + IAM   │
   │  SQLite (메타데이터)         │
   │  웹 UI (/ui)                 │
   └──┬────────────┬──────────┬───┘
      │            │          │        HTTP 양방향
  ┌───┴────┐  ┌────┴─────┐  ┌─┴──────┐
  │  app   │  │  source  │  │transform│   사용자가 평소대로 실행하는 서비스
  │+start()│  │ +start() │  │+start() │   = 그 서비스의 Worker
  └────────┘  └──────────┘  └─────────┘
```

- **엔진** (`msdf up`): 설정 파일을 들고, 요청을 받아 계획을 세우고, 단계를 서비스에 나눠 줍니다. 서비스를 띄우거나 사용자 코드를 import하지 않습니다. 코드는 `ast`로 읽기만 합니다.
- **서비스 프로세스**: 사용자가 실행합니다. `start()`가 작은 수신 서버를 띄워, 엔진이 보낸 단계를 실행합니다.
- **데이터는 엔진을 거치지 않습니다.** 서비스 프로세스가 저장소에서 직접 읽고 씁니다. 엔진은 "어디에 넣을지"와 ID 같은 메타데이터만 다룹니다.

### 통신

| 방향 | 경로 | 내용 |
| --- | --- | --- |
| 서비스 → 엔진 | `POST /register`, `/heartbeat`, `/unregister` | 기동, 생존 신고, 종료 |
| 서비스 → 엔진 | `POST /order`, `/delete` | 요청. 요청 서비스는 등록 정보로 확인 |
| 엔진 → 서비스 | `POST /run` | 단계 실행 지시. 서비스는 즉시 202를 돌려주고 백그라운드로 실행 |
| 서비스 → 엔진 | `POST /step/result` | 실행 결과. 보고에 실패하면 서비스가 다시 보낸다 |

## 엔진 구성 요소

| 구성 요소 | 책임 |
| --- | --- |
| Registry | `ast` 분석으로 서비스와 Action을 모으고 소속을 정함 |
| IAM | 요청과 DAG의 흐름이 규칙에 맞는지 판정 |
| Planner | DAG의 결과에서 거꾸로 올라가며 실행할 단계만 고름. DB에 쓰지 않는 순수 함수 |
| Artifact 테이블 | 데이터마다 출처, 생성 시각, 체크섬 같은 메타데이터를 보관. 실제 데이터는 갖지 않음 |
| Scheduler | 단계를 큐에 넣고 쉬는 서비스 인스턴스에 보냄. lease, 재시도, 실패 전파 |
| Resolver | 설정에 따라 데이터를 저장·읽기·삭제. 서비스 프로세스 안에서 돌며 저장소 종류를 아는 유일한 부분 |

## ID 두 개

| | 요청의 정체 (`lineage_key`) | 데이터의 정체 (`artifact_id`) |
| --- | --- | --- |
| 만드는 시점 | 계산 **전** | 저장 **직후** (Planner가 같은 값을 미리 계산) |
| 재료 | 서비스, Action, 버전, 출력 슬롯, 입력 슬롯별 데이터 ID, (첫 단계라면) params | 부모 데이터 ID들, 요청의 정체, 세대(generation) |
| 쓰임 | 캐시 확인, 중복 실행 방지, `order()`의 반환값 | 데이터 위치 찾기, 출처 추적 |

데이터 ID는 결정적으로 계산되므로 Planner가 실행 전에 미리 알 수 있고, 저장소가 저장할 때 같은 값을 냅니다.
두 값이 다르면 엔진이 그 단계를 실패로 처리합니다(잘못된 캐시를 내보내지 않기 위해).

## 한 단계가 실행되는 과정

```text
Scheduler ── /run ──▶ 서비스 프로세스
  1. 입력 데이터를 저장소에서 읽어 Action 인자로 넣는다
  2. Action을 실행한다 (동기 함수는 별도 스레드, async 함수는 이벤트 루프)
  3. 반환값을 출력 슬롯별로 저장하고 데이터 ID를 받는다
  4. 결과를 엔진에 보고한다 → 엔진이 메타데이터를 등록하고 다음 단계를 보낸다
```

- 한 서비스 프로세스는 **한 번에 한 단계만** 실행합니다. 처리량을 늘리려면 같은 서비스를 여러 개 띄웁니다.
- 서비스는 일정 주기로 심박을 보내고, 엔진은 그동안 그 서비스가 가진 단계의 lease를 연장합니다.

### 단계 상태

```text
queued → leased → running → saved → done
                     │
                     └──▶ failed ──▶ (의존하던 단계) cancelled
```

## 실패 처리

| 상황 | 동작 |
| --- | --- |
| Action이 예외를 냄 | `retries`만큼 재시도. 간격은 `retry_delay × 2^(시도-1)` |
| 서비스 프로세스가 죽음 | 심박이 끊기면 인스턴스를 정리하고 그 단계를 큐로 되돌려 다른 인스턴스에서 실행 (재시도 횟수는 늘지 않음) |
| 단계를 보내지 못함 | 인스턴스를 정리하고 단계를 큐로 되돌림 |
| 재시도 소진 | 단계 `failed`, 의존 단계 `cancelled`. 그 run의 `on_fail`에는 `"failed"`, 그 단계에 합류했던 다른 run의 `on_fail`에는 `"cancelled"` |
| 저장소에서 입력 데이터가 사라짐 | 그 데이터를 "유실"로 표시하고 run을 다시 계획 (최대 3번) |
| 여러 서비스가 같은 결과를 동시에 요청 | 계산은 한 번만, 배달은 요청 수만큼 |
| 엔진이 재시작됨 | 단계 상태가 DB에 있으므로 서비스가 다시 등록되면 이어서 진행 |

## 데이터 보관

- 같은 요청의 최근 N세대(`--keep-generations`), 같은 자리(같은 부모, 같은 서비스.액션.슬롯)에서 버전만 다른 결과의 최근 M개(`--keep-versions`)를 **hot**에 두고 캐시로 씁니다.
- 그보다 오래된 메타데이터는 하위 데이터와 함께 **cold**(`.msdf/cold.db`)로 옮겨 추적용으로만 남깁니다. 캐시 확인은 hot만 봅니다.
- 데이터 본체는 옮기거나 지우지 않습니다. 보관 기간은 사용자 저장소의 정책입니다.
- 부모-자식 연결은 옮기지 않으므로 hot과 cold에 걸쳐 계보를 따라갈 수 있습니다.

## 삭제

데이터는 바뀌지 않으므로 없애는 길은 `delete()` 요청뿐입니다.

1. IAM `delete` 규칙을 검사합니다.
2. 엔진이 **삭제 표시를 먼저** 남깁니다. 이 순간부터 캐시로 쓰이지 않습니다.
3. 저장소에서 본체를 지웁니다. 실패하면 표시를 둔 채 주기적으로 다시 시도합니다.

기본으로 하위 데이터는 남겨 두고, 추적에서 "부모 삭제됨"으로 보입니다. `cascade=True`면 하위까지 지웁니다.

## 엔진의 저장소

엔진은 메타데이터를 SQLite 파일(`.msdf/msdf.db`)에 둡니다.

- **DB에 쓰는 것은 엔진의 전용 스레드 하나뿐**입니다. 서비스들이 큐를 직접 읽지 않고 엔진이 밀어 주므로 SQLite의 동시 쓰기 문제가 없습니다.
- WAL 모드라 엔진이 쓰는 동안 UI가 상태를 읽을 수 있습니다.
- 0.x 동안은 버전이 바뀌어 DB 구조가 달라지면 자동 변환하지 않고 `.msdf/msdf.db`를 지우라고 안내합니다. 이 파일에는 캐시와 실행 기록만 있으므로 지워도 저장소의 실제 데이터는 그대로입니다.

## 성능

한 단계의 비용은 대부분 **데이터를 읽고 쓰는 시간**과 Action 자체의 계산입니다. 엔진의 계획·큐 처리는 밀리초 단위입니다.

- 데이터가 엔진을 거치지 않습니다.
- DataFrame은 Parquet으로 저장합니다(열 지향이라 작고 빠름).
- 캐시 히트면 그 단계는 데이터를 읽지도 않고 건너뜁니다.
- 단계마다 대기·시작·저장·완료 시각을 기록해, 어디가 느린지 UI 타임라인에서 볼 수 있습니다.

## 웹 UI

`msdf up`과 함께 `http://127.0.0.1:8787/ui`에 뜹니다. 외부 의존성이 없는 페이지 하나입니다.

- DAG를 그래프로 보고, 각 서비스가 떠 있는지 확인합니다.
- 실행(run)을 고르면 단계마다 상태, 시도 횟수, 타임라인을 보여 주고, 캐시로 건너뛴 단계는 점선으로 표시합니다.
- 실패한 단계와 원인(사용자 코드의 traceback)을 보여 줍니다.

같은 정보가 JSON API로도 있습니다: `/api/dags`, `/api/services`, `/api/runs`, `/api/runs/{run_id}`, `/api/artifacts/{artifact_id}`(계보).
