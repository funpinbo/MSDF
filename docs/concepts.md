# 핵심 개념

**한국어** | [English](en/concepts.md)

## MSDF가 해결하는 문제

마이크로서비스가 늘어나면 서비스 A가 B를 부르고, B가 C의 DB를 읽는 식으로 서로를 알게 됩니다.
그러면 흐름 하나를 바꾸려 해도 여러 서비스를 고쳐야 하고, 데이터가 어디서 왔는지, 누가 볼 수 있는지, 어디서 실패했는지 추적하기 어려워집니다.

이 문제를 처음 겪은 곳은 챗봇이었습니다. 기능이 붙을 때마다 챗봇이 전체 흐름을 지휘하게 되는 과정은 [만든 이유](background.md)에 있습니다.

MSDF는 서비스 사이를 오가는 **데이터**를 한 계층에서 관리합니다.

- 서비스는 필요한 결과물을 **이름으로 요청**만 합니다.
- 누가 어떤 순서로 만드는지는 **DAG 파일**이 정합니다.
- 누가 무엇을 요청하고 받을 수 있는지는 **IAM 파일**이 정합니다.
- 데이터가 어느 저장소에 들어가는지는 **resolvers 파일**이 정합니다.

Airflow 같은 도구가 **작업(task)** 을 기준으로 흐름을 짠다면, MSDF는 **데이터(Artifact)** 를 기준으로 짭니다.

## 하는 일과 하지 않는 일

MSDF는 **서비스 사이의 데이터 이동에서 권한, 실패, 추적을 쉽게 하는 계층**입니다. 서비스 전체를 관리하는 시스템이 아닙니다.

| 하는 일 | 하지 않는 일 |
| --- | --- |
| 요청한 결과물을 만드는 데 필요한 단계만 계산 | 서비스를 띄우거나 배포하기 |
| 데이터마다 출처(원본, 서비스, 함수, 버전)를 기록 | 같은 입력에 같은 결과가 나오도록 보장하기 (서비스의 몫) |
| 권한을 한 곳에서 검사 | DB 관리하기. 저장·삭제 요청만 보내고 보관 기간은 사용자 DB의 몫 |
| 실패한 단계부터 다시 실행 | 서비스 안의 맥락 관리. 결과를 언제 확인할지는 서비스가 정함 |

## 용어

| 용어 | 뜻 |
| --- | --- |
| **Service** | 사용자가 만든 기능 단위. `@service`로 진입점을 표시합니다. |
| **Action** | 서비스 안에서 데이터를 읽거나 쓰는 함수. `@action`으로 표시하고, 입력·출력 슬롯을 가집니다. |
| **Slot** | Action의 입력/출력 이름. 그 함수 안에서만 의미가 있습니다. 슬롯끼리의 연결은 DAG가 합니다. |
| **Param** | 요청과 함께 보내는 값. 첫 단계 Action이 이름으로 받습니다. JSON으로 바꿀 수 있어야 합니다. |
| **Order** | 결과물을 이름으로 요청하는 것. `order("daily_stats", params=...)`처럼 부르고 결과를 기다리지 않습니다. |
| **DAG** | 결과물 하나를 만드는 방법을 적은 YAML 파일. 단계, 연결, 결과 슬롯, 결과를 돌려줄 곳을 담습니다. |
| **Artifact** | 저장되어 서비스 경계를 넘는 데이터. 한 번 만들어지면 바뀌지 않습니다. |
| **Delivery** | 결과 통지. 성공하면 `on_success`, 최종 실패하면 `on_fail` Action을 깨웁니다. |
| **request_id** | 요청 하나의 ID. `order()`가 돌려주고 delivery에도 같은 값이 옵니다. 같은 데이터를 요청해도 요청마다 다릅니다. |
| **meta** | 요청에 붙여 결과와 함께 돌려받는 작은 값(예: session_id). 계산에는 쓰이지 않습니다(cache key 아님). |
| **data_version** | source 데이터의 버전. 데이터를 읽는 서비스가 `invalidate()`로 바꾸면 그 단계부터 새로 계산됩니다. |

### 무엇이 Artifact인가

서비스가 자기 안에서 만들 수 없어 다른 서비스에 요청하는 지점부터가 Artifact입니다.
서비스 안에서만 쓰고 끝나는 값, 사용자 입력 같은 외부 입력은 Artifact가 아닙니다. 모든 Artifact는 Order에서 시작합니다.

## 요청 하나가 처리되는 과정

```text
1. order        app이 order("daily_stats", params={"day": ...}, meta=...) 호출 → request_id를 받고 즉시 반환
2. 권한 검사     요청 자체와 DAG의 모든 연결이 IAM 규칙에 맞는지 확인. 하나라도 막히면 전체 거부
3. 캐시 확인     같은 요청으로 이미 만든 결과가 있고 만료되지 않았으면 그것을 쓴다
4. 계획         결과에서 거꾸로 올라가며 실제로 계산해야 할 단계만 고른다
5. 실행         각 서비스 프로세스가 자기 단계를 하나씩 실행하고 결과를 저장
6. 배달         app의 on_success(또는 on_fail)를 깨운다. request_id와 meta도 함께
```

서비스 코드에서 하는 일은 1번과 6번의 함수를 만드는 것뿐입니다. 나머지는 엔진이 처리합니다.

## 캐시: 같은 요청이면 다시 계산하지 않는다

MSDF는 **같은 입력과 같은 로직이면 같은 결과**라고 믿습니다. 그래서 계산하기 전에 "이 요청을 전에 한 적이 있는가"를 판단합니다.

같은 요청인지 판단하는 데 쓰는 것:

- 어느 서비스의 어느 Action인가
- Action의 버전 (함수 소스를 정규화한 해시. 주석, 공백, docstring, 데코레이터 옵션은 영향을 주지 않음)
- 어떤 입력 데이터가 어느 슬롯으로 들어왔는가
- 첫 단계라면 order의 params
- `invalidate()`로 알린 source 데이터의 `data_version` (한 번도 알리지 않았으면 없음)

판단에 쓰지 **않는** 것: 요청한 계정, `retries`, `fresh_for`. 그래서 다른 계정이 같은 요청을 하면 결과를 공유합니다(권한 검사는 따로 합니다).

| 무엇이 바뀌었나 | 결과 |
| --- | --- |
| 같은 날짜로 다시 요청 | 모든 단계를 건너뛰고 저장된 결과를 돌려줌 |
| `summarize` 함수 로직을 고침 | `load`, `clean` 결과는 재사용, `summarize`부터 다시 계산 |
| 다른 날짜로 요청 | 처음부터 계산 |
| `load`의 `fresh_for`가 지남 | `load`부터 새로 계산 |
| `source` 서비스가 `invalidate("load")`로 데이터가 바뀌었다고 알림 | `load`부터 새로 계산 (하위 단계는 입력이 바뀌므로 저절로 다시 계산) |
| 같은 요청이 동시에 여러 번 옴 | 계산은 한 번만, 결과는 요청 수만큼 배달 |

같은 결과가 나오도록 만드는 것(멱등성)은 서비스의 책임입니다.

## 실패: 실패한 곳부터 다시

각 단계의 결과는 저장되므로, 중간에 실패해도 처음부터 다시 할 필요가 없습니다.

- Action이 예외를 내면 `retries`만큼 다시 시도합니다.
- 서비스 프로세스가 죽으면 그 단계는 다른 인스턴스(또는 다시 뜬 프로세스)에서 다시 실행됩니다.
- 재시도를 다 써도 실패하면 그 단계는 `failed`, 그 결과에 의존하던 단계는 `cancelled`가 되고, 요청한 서비스의 `on_fail`이 깨워집니다.
- `on_fail`에는 `"failed"` 또는 `"cancelled"`만 전달됩니다. 자세한 원인은 웹 UI에서 봅니다.
- 저장소에서 입력 데이터가 사라졌다면(사용자 DB 정책으로 지워진 경우) 캐시가 없던 것으로 보고 다시 계획합니다.

## 데이터의 출처

모든 Artifact는 "어떤 원본에서, 어느 서비스의 어느 함수(버전)가 만들었는가"를 기록합니다.
결과물 하나에서 거꾸로 따라가며 어떤 데이터와 어떤 코드 버전을 거쳐 나왔는지 볼 수 있고, 같은 기록이 캐시와 재시작 지점으로도 쓰입니다.
