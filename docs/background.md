# 만든 이유

## 출발점: 챗봇이 모든 것을 떠안게 된다

요즘 챗봇은 대부분 에이전트 형태로 만들어집니다. 질문에 답하는 것에서 끝나지 않고 검색, 문서 임베딩, 요약, 외부 API 호출,
사용자 정보 조회 같은 기능이 계속 붙습니다.

문제는 기능을 붙이는 방식입니다. 새 기능이 생길 때마다 보통 챗봇 코드에 이런 것이 함께 들어갑니다.

- 어떤 기능을 어떤 순서로 부를지
- 앞 기능의 결과를 어떻게 다음 기능에 넘길지
- 결과를 어디에 저장하고, 언제 다시 만들지
- 중간에 실패하면 어디서부터 다시 할지

그러다 보면 챗봇이 **전체 로직의 지휘자(오케스트레이터)** 가 됩니다. 기능 하나를 더하거나 빼려 해도 챗봇을 고쳐야 하고,
기능끼리도 서로를 직접 부르며 얽힙니다. 챗봇이 커질수록 어디를 고쳐야 무엇이 바뀌는지 알기 어려워집니다.

```text
지금 흔한 모습                              바라는 모습

chatbot ─┬─▶ search                         chatbot ──"이 결과가 필요하다"──▶ MSDF
         ├─▶ embedding                                                        │
         ├─▶ summarize                       search ─▶ embedding ─▶ summarize ◀┘
         └─▶ (새 기능마다 여기에 추가)         (연결은 DAG 파일에만 있다)
```

## 챗봇은 데이터 변화가 많다

챗봇은 특히 데이터를 많이 바꿉니다.

- 질문이 올 때마다 새로운 검색 결과와 중간 데이터가 생깁니다.
- 원천 문서가 갱신되고, 임베딩 모델이나 요약 방식이 바뀝니다.
- 같은 질문이 반복되기도 하고, 거의 같은 데이터를 여러 기능이 다시 만들기도 합니다.

그래서 "무엇이 바뀌었고, 무엇을 다시 계산해야 하는가"에 민감하게 반응해야 합니다. 이 판단을 각 기능이 따로 하면 같은 계산을 반복하거나,
바뀐 데이터를 놓쳐 옛 결과를 쓰게 됩니다.

## 그래서 이렇게 정했다

**오케스트레이션을 기능 밖으로 꺼낸다.** 각 기능(서비스)은 자기 일만 합니다. 누가 어떤 순서로 이어지는지는 DAG 파일 한 곳에 둡니다.

**서비스는 서로를 모른다.** 서비스는 필요한 결과물을 이름으로 요청할 뿐, 그 결과를 누가 만드는지 모릅니다.
기능을 더하거나 빼도 다른 서비스 코드는 그대로이고, DAG만 바뀝니다.

**데이터 변화를 기준으로 움직인다.** 흐름의 단위를 작업(task)이 아니라 데이터(Artifact)로 잡습니다. 데이터마다 어디서 왔고
어떤 코드(버전)가 만들었는지를 기록하므로, 바뀐 곳부터만 다시 계산하고 바뀌지 않은 결과는 재사용합니다.

**권한, 실패, 추적은 한 곳에서.** 기능이 늘어도 "누가 이 데이터를 받을 수 있나", "어디서 실패했나", "이 결과는 어디서 왔나"를
한 곳에서 봅니다.

## 예: 기능을 하나 더할 때

검색한 문서를 요약하기 전에 번역하는 기능을 넣는다고 해 봅시다.

**MSDF 없이** — 챗봇 코드를 고칩니다.

```python
def answer(question):
    docs = search(question)
    docs = translate(docs)          # 새로 추가: 챗봇이 순서를 알아야 한다
    vectors = embed(docs)
    return summarize(vectors)
```

**MSDF로** — 번역 서비스를 만들고 DAG에 노드 하나와 연결을 더합니다. 챗봇 코드는 바뀌지 않습니다.

```python
# translate.py — 새 서비스. 자기 일만 선언한다
@service("translate")
def translate(): ...

@action(inputs=["docs"], outputs=["out"])
def to_korean(docs): ...
```

```yaml
# dags/search_result.yaml — 바뀌는 곳은 여기뿐
nodes:
  fetch:     {service: search,     action: fetch}
  translate: {service: translate,  action: to_korean}   # 추가
  embed:     {service: embedding,  action: embed}
  refine:    {service: processing, action: refine}

edges:
  - {from: fetch.out,     to: translate.docs}           # 바뀜
  - {from: translate.out, to: embed.docs}               # 추가
  - {from: embed.out,     to: refine.vectors}
```

다음 요청부터는 검색 결과는 캐시에서 재사용하고, 번역부터 다시 계산합니다. 번역을 빼고 싶으면 DAG에서 노드를 지우면 됩니다.
웹 UI의 DAG 편집기에서 노드를 끌어다 놓아도 같은 파일이 만들어집니다.

## 챗봇에서 시작했지만

이 문제는 챗봇에서 처음 겪었지만 챗봇만의 문제는 아닙니다. 여러 서비스가 데이터를 주고받고, 기능이 자주 바뀌고,
데이터가 자주 갱신되는 곳이면 같은 문제가 생깁니다. MSDF는 그런 곳에서 **서비스 사이의 데이터 이동**만 맡는 계층입니다.
서비스를 띄우거나 배포하는 일, 서비스 안의 로직은 다루지 않습니다([핵심 개념](concepts.md#하는-일과-하지-않는-일)).
